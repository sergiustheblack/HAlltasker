# HAlltasker — техническое задание (v1.4, 2026-11-01)

> Язык: русская копия для чтения (основной язык для людей). Обязательная версия для агентов — английская: [docs/SPEC.md](../SPEC.md). При расхождении действует английская.

Статус: утверждено к разработке. Изменения только через правку этого файла. Изменения относительно v1.0 перечислены в §9, относительно v1.1 — в §10, относительно v1.2 — в §11, относительно v1.3 — в §12.

## 1. Цель

Двусторонняя синхронизация задач и напоминаний между экосистемами (Яндекс Алиса, Apple Reminders, Google Tasks, списки Home Assistant). Задача, созданная в одной системе, появляется и поддерживается в согласованном состоянии в остальных. Реализуется как custom integration для Home Assistant (далее HA), устанавливается через HACS.

## 2. Ключевые решения

| Вопрос | Решение |
|---|---|
| Платформа, язык | Custom integration HA, Python 3.14+, стабильная HA 2026.9.x |
| Граница ответственности | Ядро не содержит авторизации и приватных API внешних систем. Единственный источник данных в MVP — сущности HA `todo.*`, созданные другими интеграциями или собственной платформой `todo` для CalDAV в HAlltasker (FR-13). После MVP (решение от 2026-10-28, IT-41): если есть stock- или community-интеграция HA, которая даёт доступ к системе и удовлетворяет сценарию, HAlltasker использует её через плагин и своего клиента не добавляет; только если такой интеграции нет, плагин может нести собственный API-клиент, с учётными данными в YAML через `!secret` и никогда в ядре |
| Apple Reminders | Через штатную интеграцию HA CalDAV к iCloud (`caldav.icloud.com`) |
| Google Tasks | Через штатную интеграцию HA Google Tasks |
| Яндекс | Через собственную платформу `todo` для CalDAV в HAlltasker (FR-13) к `caldav.yandex.ru` (дела Календаря); код адаптирован из HA core `caldav`. Штатная HA CalDAV для Яндекса не используется: она не видит закрытие, сделанное в Яндекс Календаре (RESEARCH §1, IT-48), и открывает все коллекции, тогда как Алиса добавляет дела только в «Мои дела». Напоминания Алисы с временем в CalDAV не попадают (этап 0, RESEARCH §4); они читаются и пишутся через приватный API напоминаний приложения Алисы с авторизованной сессией установленной интеграции YandexStation — собственная платформа `todo` для напоминаний в HAlltasker (FR-14). HAlltasker не хранит учётных данных Яндекса |
| Конфигурация | **Только YAML** (`configuration.yaml`). Config/options flow в UI вне MVP. Техническая деталь: import-flow создаёт одну ConfigEntry из YAML для reload и diagnostics |
| Конфликты | Политика на пару: `prefer_a` (дефолт) или `prefer_b`. Поля, изменённые только с одной стороны, объединяются. Настоящий last-write-wins невозможен: HA не отдаёт время изменения задач |
| Маршрутизация | Пары узлов A↔B, у каждой пары правила на направление A→B и B→A. Узел может входить в несколько пар (FR-12); пары не должны образовывать цикл |
| Объём синхронизации | create, update полей, complete/uncomplete, delete. Всё включается и выключается в правилах |
| Уведомления | Дубли уведомлений от разных систем принимаются, ядро не вмешивается |
| Пользователи | Один. Многоаккаунтность не блокируется: узел = любая сущность `todo.*`, их может быть сколько угодно |
| Повторяющиеся задачи | Вне scope полностью |
| Список покупок Яндекса | Вне первой итерации. Позже через существующий мост YandexStation |

## 3. Область MVP

Входит:

- Каноническая задача: `title`, `description`, `status` (open/done), `due` (нет, дата, или дата+время с часовым поясом), `extensions`.
- Один плагин `ha_todo`: любая сущность `todo.*` как узел. Покрывает CalDAV (iCloud, Яндекс), Google Tasks, Local To-do, Shopping List и будущие интеграции без нового кода.
- Собственная платформа `todo` для CalDAV (FR-13): выбранные коллекции VTODO учётной записи CalDAV становятся сущностями `todo.*` с семантикой выполненности по RFC 5545. Обязательна для Яндекса; работает с любым CalDAV-сервером.
- Собственная платформа `todo` для напоминаний Алисы (FR-14): напоминания учётной записи с временем становятся одной сущностью `todo.*` (заголовок + дата-время), сессию даёт интеграция YandexStation.
- Пары узлов с правилами на направление: разрешённые операции, фильтры, трансформации.
- Внутреннее хранилище связей и tombstone в `.storage/halltasker`.
- Первичная синхронизация в режимах `merge` (дефолт) и `dry_run`.
- Polling с интервалом на пару, реакция на события HA как ускорение.
- Сервисы `halltasker.sync_now`, `halltasker.dry_run`; сенсор состояния на пару; diagnostics без секретов.

Не входит:

- RRULE, подзадачи, вложения, теги, приоритеты, геонапоминания, порядок элементов.
- Заметки, события календарей, таск-трекеры, список покупок. Закладываются архитектурой как будущие плагины (`docs/ARCHITECTURE.md` §13). События календарей — только идея с низким приоритетом (решение от 2026-10-28).
- UI конфигурации, подавление дублей уведомлений, собственные клиенты внешних API (после MVP допускаются по правилу §2).

## 4. Термины

- **Узел (Node)** — конкретный список задач в конкретной системе. В MVP узел задаётся строкой `todo.<entity_id>`.
- **Плагин (Plugin)** — внутренний модуль HAlltasker с единым контрактом (§6.2): описывает свои возможности, читает и пишет узлы, преобразует свою модель в каноническую и обратно. Плагин не является отдельной HA-интеграцией.
- **Каноническая задача (CanonicalTask)** — внутреннее представление задачи, общее для всех плагинов.
- **Снапшот (Snapshot)** — сериализованная каноническая задача плюс её хеш.
- **Связь (Link)** — запись «каноническая задача ↔ внешний id в узле» с тремя снапшотами (`last_observed`, `last_written`, `last_synced`) и флагом `tombstone`.
- **Пара (SyncPair)** — два узла A и B, интервал опроса, политика конфликтов, режим первичной синхронизации, правила направлений.
- **Правило направления (DirectionRule)** — для направления X→Y: какие операции разрешены (`create`, `update`, `complete`, `delete` со значениями true/false/soft), фильтр, трансформации.
- **Capabilities** — набор полей и операций, которые поддерживает конкретный узел. Для `todo.*` читается из атрибута `supported_features`.
- **Понижение (Downgrade)** — приведение канонической задачи к возможностям узла (например, `datetime` → `date` для Google Tasks). Понижение не является изменением и не создаёт конфликт.
- **Echo** — чтение из узла значения, которое ранее записал сам HAlltasker. Echo не является изменением.
- **Tombstone** — пометка связи как удалённой. Запрещает повторное создание и повторную обработку.

## 5. Функциональные требования

### FR-1 Плагин `ha_todo`

1. Узел = `entity_id` домена `todo`.
2. Чтение через сервис `todo.get_items` с `return_response=True`. Запись через `todo.add_item`, `todo.update_item`, `todo.remove_item` с `blocking=True`.
3. Capabilities читаются из `supported_features` состояния сущности: `CREATE_TODO_ITEM=1`, `DELETE_TODO_ITEM=2`, `UPDATE_TODO_ITEM=4`, `SET_DUE_DATE_ON_ITEM=16`, `SET_DUE_DATETIME_ON_ITEM=32`, `SET_DESCRIPTION_ON_ITEM=64`. Операция или поле, не поддерживаемые узлом, не вызываются.
4. После `add_item` плагин повторно читает список и находит созданный элемент по совпадению содержимого среди элементов, не имеющих связи. Это единственный способ получить `uid`, так как сервис не возвращает ответ.
5. Если сущность отсутствует или недоступна (`unavailable`, `unknown`) — узел считается недоступным, пара пропускается с ошибкой в сенсоре.

### FR-2 Каноническая модель и схема плагина

1. `CanonicalTask`: `title: str`, `description: str | None`, `status: "open" | "done"`, `due: None | date | datetime` (datetime обязательно с tzinfo), `extensions: dict[str, Any]`.
2. Дата без времени хранится как `date`. Запрещено представлять её как `datetime` с полуночью.
3. Плагин объявляет схему: поддерживаемые канонические поля, ограничения на поля (`due: datetime | date_only | none`), поддерживаемые операции, собственные поля-расширения.
4. Понижение при записи выполняется ядром по capabilities узла: `datetime` → `date` в локальном часовом поясе HA, если узел не поддерживает время; `due` отбрасывается, если узел не поддерживает дату; `description` отбрасывается, если не поддерживается.
5. При сравнении прочитанного значения с ожидаемым ядро сравнивает пониженные формы. Прочитанная дата при ожидаемом datetime — не изменение.
6. Расширения (`extensions`) передаются только узлам, чей плагин объявил соответствующее поле. В MVP плагин `ha_todo` расширений не объявляет.

### FR-3 Маршрутизатор

1. Для каждой пары и каждого направления заданы: `create`, `update`, `complete` (true/false), `delete` (true/false/soft) с модификатором `delete_past_due` (true/false, FR-6.7), `filter` (`title_regex`, `require_due`: false | true | `datetime`, где `datetime` пропускает только задачи, у которых `due` содержит время), `transform` (`due: keep | date_only | drop`, `title_prefix`).
2. Дефолт: все операции разрешены, `delete: true`, фильтра нет, трансформаций нет.
3. Фильтр применяется к канонической задаче источника до записи. Задача, не прошедшая фильтр при создании, не создаётся на другой стороне и не линкуется с ней.
4. Трансформация применяется после фильтра и до понижения.
5. Изменение на одной стороне, которое правило направления не распространяет (операция выключена или задача не прошла фильтр), принимается на этой стороне как новое синхронизированное состояние. Оно не фиксируется повторно в следующих циклах и не протекает на другую сторону через последующее объединение.

### FR-4 Обнаружение изменений и echo

1. Для каждой связи и каждой стороны: текущее значение сравнивается по хешу с `last_observed`. Совпадение — нет изменений.
2. Если текущее значение совпадает с `last_written` — это echo: обновляется `last_observed`, изменение не фиксируется.
3. Иначе — изменение. Набор изменённых полей вычисляется относительно `last_synced`.
4. Отсутствие элемента в успешно прочитанном полном списке — удаление.

### FR-5 Разрешение конфликтов

1. Изменение только с одной стороны распространяется на другую по правилу направления.
2. Изменения с двух сторон с непересекающимися наборами полей объединяются. Результат объединения записывается на сторону, только если правило направления к ней разрешает `update` (или `complete`) и узел это поддерживает (FR-1.3). Если ни на одну сторону писать нельзя, оба изменения принимаются локально (FR-3.5).
3. Пересекающиеся поля берутся со стороны, указанной политикой пары (`prefer_a` дефолт, `prefer_b`).
4. Удаление с одной стороны и изменение с другой: `prefer_a`/`prefer_b` определяет, побеждает ли удаление (если удалена предпочитаемая сторона) или воссоздание (если разрешён `create` в направлении к удалившей стороне). Иначе связь получает tombstone без действий.

### FR-6 Удаление

1. Удаление распространяется только если: чтение узла-источника завершилось без ошибки, список прочитан полностью, элемент отсутствует, связь не tombstone.
2. При `delete: false` в направлении — обе связи задачи в этой паре получают tombstone, на другой стороне ничего не меняется, элемент другой стороны исключается из обнаружения новых в этой паре.
3. При `delete: soft` — на другой стороне элемент отмечается выполненным, обе связи получают tombstone.
4. При `delete: true` — элемент удаляется на другой стороне, обе связи получают tombstone.
5. Tombstone хранится не менее 30 дней. После этого он удаляется в конце цикла синхронизации, но только если элемент, на который он указывает, отсутствует в узле. Tombstone, чей элемент всё ещё существует в узле (случай `delete: false`), не удаляется никогда, чтобы элемент не появился снова как новый.
6. Tombstone принадлежит одной паре. Другие пары, содержащие тот же узел, видят удаление или запись «выполнено» как обычное изменение и применяют свои правила (FR-12).
7. `delete_past_due: false` в направлении X→Y: если элемент на X исчез, а его последний синхронизированный `due` уже прошёл (дата-время не позже «сейчас» или дата раньше сегодняшней в часовом поясе HA), удаление обрабатывается как `delete: false` — только tombstone, Y не трогается. Удаление до срока следует `delete` как обычно. По умолчанию `true` (прежнее поведение). Цель: сработавшее и исчезнувшее напоминание не должно удалять свой дубль в других системах, а отменённое заранее — должно.

### FR-7 Идемпотентность и хранилище

1. Связи хранятся только во внутреннем `Store` HA (`.storage/halltasker`). В задачи пользователя не добавляются маркеры, префиксы или скрытые поля.
2. Хранилище сохраняется после каждой успешной операции записи во внешний узел, чтобы сбой между записью и сохранением не приводил к дублю.
3. Повторный запуск цикла без внешних изменений не производит ни одной записи.

### FR-8 Первичная синхронизация

1. Режим `merge` (дефолт): все нелинкованные элементы обеих сторон создаются на противоположной стороне по правилам направления. Удаления на первом цикле не выполняются.
2. Режим `dry_run`: цикл вычисляет действия и публикует их в сенсор и ответ сервиса, записей не делает. Пара в `dry_run` остаётся в нём до смены конфигурации.
3. Эвристика сопоставления перед созданием: пара нелинкованных элементов с равными `title` и равным пониженным `due` считается одной задачей и линкуется без создания. Эвристика никогда не используется для удаления.
4. Сопоставление «сирот»: перед созданием линкованной задачи на стороне, где её связь отсутствует, нелинкованные элементы этой стороны просматриваются той же эвристикой. Совпадение линкуется вместо создания. Это покрывает `create`, при котором элемент записан, но uid не найден (FR-1.4), чтобы дубли не появлялись ни на одной стороне. Известное ограничение: если на этой стороне лежат и сирота, и действительно новый элемент с теми же `title` и `due`, линкуется первый, а второй считается новым; допущение то же, что в п. 3.

### FR-9 Опрос и события

1. Каждая пара опрашивается с интервалом `interval` секунд (дефолт 60, минимум 15).
2. Изменение состояния любой сущности узла (событие `state_changed`) запускает внеочередной цикл для пар с этой сущностью, с задержкой 2 секунды для склейки событий. События — ускорение; polling обязателен, потому что изменение названия или даты не меняет состояние `todo.*`.
3. Ошибка одной пары не влияет на другие пары.
4. Цикл ограничен 120 секундами. Цикл, превысивший лимит, — ошибка этой пары; остальные пары работают как обычно. Прерывание цикла не создаёт дублей (FR-7.2, FR-8.4).

### FR-10 Сервисы, сенсоры, диагностика

1. `halltasker.sync_now` с необязательным `pair_id`: немедленный цикл.
2. `halltasker.dry_run` с необязательным `pair_id`: возвращает список планируемых действий без записи.
3. Сенсор на пару `sensor.halltasker_<pair_id>`: состояние `ok | error | dry_run | disabled`; атрибуты `last_run`, `links`, `last_error`, `last_actions` (счётчики по типам), `planned_actions` (для dry_run).
4. `diagnostics.py` выгружает конфигурацию и хранилище. Секретов в HAlltasker нет по построению; названия и описания задач в выгрузке скрываются, хэши, статусы и даты сохраняются.
5. `halltasker.reload` (admin-сервис, без параметров): повторно читает секцию `halltasker:` из `configuration.yaml`, валидирует её и перезапускает интеграцию с новой конфигурацией. При ошибке валидации сохраняется работающая конфигурация, ошибка пишется в лог. `homeassistant.reload_config_entry` не перечитывает YAML и поэтому не является способом применить изменения конфигурации.

### FR-11 Конфигурация YAML

Полная схема в `docs/ARCHITECTURE.md` §7. Ошибка схемы — интеграция не стартует и пишет понятное сообщение в лог. Повторная загрузка через сервис `halltasker.reload` (FR-10.5) или перезапуск HA.

### FR-12 Несколько пар на узел

1. Одна и та же сущность `todo.*` может быть узлом нескольких пар, например `yandex ↔ icloud`, `yandex ↔ google`, `yandex ↔ home_list`.
2. Каждая пара хранит свои связи и tombstone. Запись, которую одна пара делает в общий узел, — обычное внешнее изменение для каждой другой пары, содержащей этот узел; так изменение проходит через пары. Ни одна пара не читает связи другой пары.
3. Ограничения конфигурации, проверяемые при загрузке: два узла пары различны; никакие две пары не соединяют одни и те же два узла; пары не образуют цикл (граф узлов и пар — лес). Нарушение — ошибка конфигурации (FR-11).
4. Циклы синхронизации разных пар никогда не выполняются одновременно.
5. Если существующий id пары указан на другие узлы, её сохранённые связи отбрасываются с предупреждением в логе, и следующий цикл этой пары — первичная синхронизация (FR-8).
6. После того как пара записала в узел, остальные пары, содержащие этот узел, запускаются вне расписания (с задержкой из FR-9.2), поэтому изменение проходит через несколько пар за секунды, а не за интервал опроса на каждую пару.

### FR-13 Платформа `todo` для CalDAV

1. Секция YAML `halltasker:` может содержать `caldav:` — список учётных записей CalDAV (`id`, `url`, `username`, `password`, `verify_ssl`, `interval`), у каждой `lists`: коллекции VTODO, которые нужно открыть, заданные `id` и ровно одним из `name` (displayname коллекции) или `href` (путь коллекции). Учётные данные приходят из YAML через `!secret`; HAlltasker своих учётных данных не хранит.
2. Каждый выбранный список становится одной сущностью `todo.*` HAlltasker: `todo.halltasker_<id списка>`. Не перечисленные коллекции не открываются. Перечисленная коллекция, которой нет на сервере, один раз пишется в лог как ошибка; сущность существует, но `unavailable`.
3. Сущность поддерживает создание, изменение, удаление, дату, дату-время и описание (`supported_features` 119, без MOVE) — ровно как штатная CalDAV todo-сущность, поэтому плагин `ha_todo` и ядро не меняются.
4. Выполненность читается по RFC 5545: `STATUS` `COMPLETED`/`CANCELLED` → `completed`; без `STATUS` — наличие свойства `COMPLETED` или `PERCENT-COMPLETE:100` → `completed`; иначе `needs_action`. Закрытие из HA пишет `STATUS:COMPLETED`, `PERCENT-COMPLETE:100` и `COMPLETED:<сейчас UTC>` (сохраняется, если уже есть); переоткрытие пишет `STATUS:NEEDS-ACTION` и удаляет `COMPLETED` и `PERCENT-COMPLETE`.
5. VTODO без `DTSTAMP` (Яндекс) принимается при чтении и получает `DTSTAMP` при записи.
6. Список обновляется каждые `interval` секунд (по умолчанию 300, минимум 60) и сразу после каждой записи через сущность. Неудачное обновление делает сущность `unavailable` до следующего удачного; пара тогда видит `NodeUnavailable` (FR-1.5).
7. Платформа — тонкая адаптация HA core `caldav` (`todo.py`, `api.py`), хранится в этом репозитории без платформы календаря и без config flow. Использует библиотеку `caldav`, закреплённую на версии закреплённого HA core.

### FR-14 Платформа `todo` для напоминаний Алисы

1. Секция `halltasker:` может содержать `yandex_reminders:` — список узлов напоминаний: `id`; необязательный `account` = unique id (логин) записи конфигурации YandexStation; необязательный `device` = имя колонки или device id quasar для напоминаний, создаваемых из HA (по умолчанию первая колонка); `push` (по умолчанию false); `interval` в секундах (по умолчанию 60, минимум 30). Без `account` используется единственная запись YandexStation; несколько записей без `account` делают узел `unavailable` с ошибкой в логе.
2. Каждый узел становится одной сущностью `todo.halltasker_<id>` с `supported_features` = создание, изменение, удаление, дата-время (без даты без времени и без описания; значение 39). Правило направления в сторону такого узла обязано задавать `filter.require_due: datetime` (проверяется при загрузке).
3. Авторизация принадлежит интеграции YandexStation: HAlltasker берёт живую авторизованную сессию её загруженной записи и шлёт запросы к приватному API напоминаний приложения Алисы с теми же заголовками, что YandexStation использует для будильников. HAlltasker не хранит токены и cookies. Если YandexStation не загружен или записи нет, сущность `unavailable`, поиск повторяется на каждом интервале.
4. Отображение: `id` напоминания → `uid`, `text` → `summary`, дата-время разового срабатывания → `due` (трактуется в часовом поясе HA, если этап 1 не покажет иного), `status = needs_action`. Напоминания с любой другой политикой срабатывания (повторяющиеся) игнорируются.
5. Запись: создание элемента создаёт напоминание на настроенной колонке с текстом и временем элемента; переименование или перенос времени изменяет напоминание, если API это даёт (этап 1), иначе запись завершается ошибкой в логе, а в паре нужно поставить `update: false` в сторону узла; `status: completed` отменяет напоминание и удерживает элемент в сущности как `completed` в локальном хранилище до истечения суток после его времени, чтобы движок видел подтверждённое выполнение, а не удаление; удаление элемента отменяет напоминание. Переоткрытие отменённого напоминания не поддерживается.
6. Этап 1 (RESEARCH §2b) фиксирует endpoint-ы записи, поведение сработавших напоминаний и часовой пояс до реализации пути записи; путь чтения (напоминания → другие системы) от него не зависит.

## 6. Нефункциональные требования

1. Код по стандартам HA core: asyncio, типизация, `ruff` без замечаний, конфигурация в `pyproject.toml`.
2. Тесты: `pytest` + `pytest-homeassistant-custom-component`. Ядро (`core/`) тестируется без HA. Плагин `ha_todo` тестируется с подменой сервисов. Дополнительно end-to-end тесты вызывают реальные сервисы `todo.*` HA на in-memory платформе `todo`, определённой внутри `tests/`. Покрытие ядра не ниже 90 %.
3. Логи: `INFO` одна строка на цикл пары с счётчиками, `DEBUG` детали действий, `WARNING` на ошибки узлов. Содержимое задач в логах только на `DEBUG`.
4. HACS: `hacs.json`, `manifest.json` с версией, проходят `hassfest` и `hacs/action`.
5. Внешние зависимости: только то, что уже есть в HA, плюс библиотеки CalDAV из FR-13.7 (`caldav`, `icalendar`, `vobject`), закреплённые на точных версиях манифеста HA core `caldav` для закреплённого релиза HA. Других пакетов в `requirements` манифеста нет.

## 7. Приёмочные сценарии

Разделены по уровню уверенности.

### A. Ядро и подтверждённые `todo.*` (обязательно)

Окружение: две сущности `local_todo` в тестовом HA.

1. Создание в A → появляется в B с теми же `title`, `due`, `description`.
2. Изменение `title` в B → меняется в A. Повторный цикл не делает записей.
3. `status: done` в A → `done` в B; `open` обратно → `open` в B.
4. Удаление в A при `delete: true` → удалено в B; при `delete: soft` → `done` в B; при `delete: false` → B без изменений, A не воссоздаётся.
5. Одновременное изменение `title` в A и `due` в B → оба изменения применены с обеих сторон.
6. Одновременное изменение `title` с обеих сторон → побеждает сторона по политике.
7. Узел B с `supported_features` без `SET_DUE_DATETIME_ON_ITEM`: `due` с временем из A записывается как дата в B; обратное чтение даты не считается изменением.
8. `dry_run`: действия перечислены, записей нет.
9. Первичная синхронизация `merge` с существующими одинаковыми задачами с обеих сторон: линкуются без дублей.
10. Три узла A, B, C и две пары A↔B, B↔C. Создание в A → появляется в B после цикла первой пары и в C после цикла второй пары. Удаление в A при `delete: true` в обеих парах → удалено в B, затем в C. Повторные циклы обеих пар не делают записей.
11. Направление A→B с `update: false`. Изменение `title` в A → B без изменений; последующее изменение `due` в B → `due` меняется в A, `title` в B остаётся прежним.
12. `create` в B выполнен, но поиск uid не удался (имитация): следующий цикл линкует элемент-сироту в B вместо создания второго; дублей нет ни в A, ни в B.

### B. Интеграционные тесты со штатными интеграциями (обязательно, вручную)

1. Пара `local_todo` ↔ Google Tasks: сценарии A1–A4, A7.
2. Пара `local_todo` ↔ iCloud CalDAV: сценарии A1–A4. Требование к окружению: на iPhone iCloud подключён как CalDAV-аккаунт или используется список, не мигрированный в «upgraded» Reminders.

### C. Яндекс (experimental, по результатам этапа 0)

1. Пара `todo.halltasker_moi_dela` (FR-13, список Яндекса «Мои дела») ↔ `local_todo`: «Алиса, добавь в список дел на сегодня помыть полы» → задача с `due` сегодня появляется в `local_todo` не позднее двух интервалов списка (FR-13.6).
2. Голосовое напоминание с временем: «Алиса, напомни сегодня в 19:00 помыть полы» → проверяется, попадает ли в CalDAV с временем. Результат фиксируется в `docs/RESEARCH.md`. Невыполнение этого сценария не блокирует релиз MVP.
3. Выполненность в обе стороны через FR-13: закрыть дело в Яндекс Календаре → `done` в `local_todo` в пределах одного интервала списка; закрыть в `local_todo` → дело показано выполненным в Яндекс Календаре и Алиса его больше не зачитывает. Переоткрытие с любой стороны → `open` на другой.
4. Напоминание → iCloud (FR-14; пара `todo.halltasker_alice` ↔ список iCloud, `a_to_b: {delete: true, delete_past_due: false}`, `b_to_a: {create: false, update: false, filter: {require_due: datetime}}`): «Алиса, напомни завтра в 10:00 проверить почту» → элемент с `due` завтра 10:00 появляется в iCloud в пределах интервала узла плюс интервала пары; отмена напоминания голосом до 10:00 удаляет элемент в iCloud; после срабатывания элемент в iCloud остаётся; завершение элемента в iCloud отменяет напоминание, а элемент в HA становится `done`.

## 8. Риски

| Риск | Митигация |
|---|---|
| Напоминания Алисы не попадают в CalDAV | FR-14 читает и пишет их через приватный API приложения Алисы с сессией YandexStation; API неофициальный и может измениться, поэтому узел изолирован в одном модуле платформы, остальная интеграция от него не зависит |
| Яндекс отмечает выполнение только `COMPLETED`; штатная HA CalDAV читает только `STATUS` и обновляется раз в ~15 мин | Собственная платформа `todo` для CalDAV (FR-13) с правилами выполненности по RFC 5545 и своим интервалом |
| iCloud CalDAV не видит «upgraded» списки | Требование к окружению в README |
| Google Tasks теряет время дня | Понижение `date_only`, не конфликт |
| Сервис `add_item` не возвращает uid | Повторное чтение и сопоставление по содержимому (FR-1.4) |
| Дубли при сбое между записью и сохранением хранилища | Сохранение после каждой записи (FR-7.2) |
| HA переводит свои схемы с voluptuous на probatio (probatio поставляется с 2026.9; большая часть core всё ещё на voluptuous) | Схема изолирована в одном файле `schema.py`; версия HA зафиксирована в `requirements_dev.txt`; перепроверять при каждом обновлении HA |
